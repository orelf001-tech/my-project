> מטרת המסמך: להגדיר איך לקוח/ה מקבל/ת קישור לטופס נקי, ממלא/ת אותו, והנתונים מגיעים מוצפנים ישירות למערכת של המאמנת, אל תצוגה מלאה וחכמה יותר. רק אחרי אישור המסמך מתחילים לכתוב קוד.

## 1. מה קיים היום (ממצאים מהמערכת הנוכחית)

המערכת ״ניהול תזרים״ היא קובץ HTML יחיד (כ־296KB) שרץ כ־Artifact ב־claude.ai:

| נושא | איך זה עובד היום | המשמעות לדרישה החדשה |
|---|---|---|
| שמירת נתונים | `localStorage` בדפדפן של המאמנת בלבד (`cashflow-system-v2`), ועוד 7 גיבויים יומיים | אין שרת, ולכן אין לאן לשלוח טופס |
| ריבוי לקוחות | כל הלקוחות באותו דפדפן, ומתחלפים ברשימה שבראש הדף | צריך מזהה לקוח יציב (`client.id` קיים) |
| מבנה נתונים | קטגוריות קבועות (`CATS`: הכנסות, משתנות, מגורים, מנויים, תחבורה, רפואה, ביטוחים, עסקאות תשלומים, הלוואות ועוד) וסעיפי ברירת מחדל (`DEFAULTS`) | הטופס יכול למפות כל שדה ישירות לקטגוריה ולסעיף |
| דוח ראשוני | טעינת תדפיסי אשראי ועו״ש, זיהוי עמודות, הצלבה ושיוך (`autoImportFile`) | לקוח יכול להעלות תדפיסים בטופס, והם ייכנסו לאותו מנגנון |
| מסירה ללקוח | ייצוא JSON ידני (״קובץ ללקוח״ / ״מצב לקוח״) | ידני, לא מוצפן, ולא חוזר אוטומטית |

**מגבלה מרכזית:** Artifact לא יכול לשמש מערכת שמקבלת טפסים מלקוחות. אין לו שרת שאפשר לסמוך עליו, ונתונים משותפים ב־Artifact גלויים לכל מי שפותח אותו, כלומר לקוחות היו רואים זה את זה. לכן המערכת עוברת לריפו ב־GitHub ולאירוח עצמאי.

## 2. דרישות

### דרישות פונקציונליות
1. **קישור אישי לכל לקוח:** המאמנת לוחצת ״שליחת שאלון״ בתיק הלקוח ומקבלת קישור לשליחה בוואטסאפ או במייל.
2. **טופס נקי ללקוח:** מותאם לטלפון, בעברית, בשלבים, בלי מונחים מקצועיים, עם שמירת טיוטה אוטומטית.
3. **קליטה אוטומטית:** הטופס שהוגש מופיע אצל המאמנת ב״תיבת שאלונים״ ונכנס לתיק הלקוח הנכון בלחיצה אחת, או אוטומטית לפי הגדרה.
4. **תצוגת מאמנת חכמה:** אותן תשובות, ולצידן שדות שרק המאמנת רואה (הערות, דגלים, המלצות), חישובים (יחס הוצאות להכנסות, החזר חובות, שיעור חיסכון) והשוואה בין מה שהלקוח דיווח לבין מה שעלה מהתדפיסים.
5. **מעקב סטטוס:** נשלח, נפתח, בתהליך, הוגש, נקלט, פג תוקף.
6. **(שלב 2)** העלאת תדפיסים מתוך הטופס, מילוי מראש של חלק מהשדות, והתראה במייל על טופס חדש.

### דרישות לא פונקציונליות
- **אבטחה:** הצפנה מקצה לקצה. השרת לא מסוגל לקרוא את הנתונים, גם אם הוא נפרץ.
- **פרטיות:** שומרים כמה שפחות. על השרת אין שם לקוח, ומה שהוגש נמחק ממנו אחרי הקליטה.
- **נוחות:** ללקוח: קישור אחד, בלי הרשמה ובלי סיסמה. למאמנת: כניסה אחת עם קוד במייל ואימות דו־שלבי, ומשם הכול באותה מערכת.
- **עלות:** 0 עד כ־100 ₪ בחודש.
- **תחזוקה:** בלי שלב build. JavaScript רגיל (Vanilla JS) כמו בקוד הקיים, וכל שינוי עובר דרך GitHub.
- **נגישות:** WCAG 2.0 AA (ת״י 5568), כי הטופס פונה לציבור.

### 4.1 רכיבים
| רכיב | טכנולוגיה | אחריות |
|---|---|---|
| `apps/coach` | HTML ו־JS רגיל (המערכת הקיימת) | המערכת הקיימת, ובנוסף: יצירת קישורים, תיבת שאלונים, פענוח, קליטה ותצוגת מאמנת |
| `apps/form` | HTML ו־JS רגיל, בלי תלויות חיצוניות | טופס הלקוח: אשף שלבים, טיוטה, הצפנה והגשה |
| `shared/schema` | JSON ו־JS | **מקור אמת יחיד** לשדות הטופס, עם שני ״פרופילים״: לקוח ומאמנת |
| `shared/crypto` | WebCrypto מובנה בדפדפן | הצפנה ופענוח של מעטפות |
| `supabase/` | Postgres, RLS, RPC ו־Edge Functions | תיבת הדואר המוצפנת, טוקנים וסטטוסים |
| אירוח | Netlify, מחובר לריפו ב־GitHub | שני אתרים מאותו ריפו, HTTPS, כותרות אבטחה ותצוגה מקדימה לכל שינוי |

**הפרדת דומיינים:** המערכת שלך (`app.`) והטופס הציבורי (`form.`) יושבים בשני דומיינים נפרדים. `localStorage` מופרד לפי דומיין, כך שגם אם תתגלה פרצה בטופס הציבורי, היא לא תגיע לנתונים של כל הלקוחות במכשיר שלך.

### 4.2 שני הטפסים: מקור אחד, שתי תצוגות
```
schema (סעיפים → שדות → מיפוי לקטגוריה וסעיף במערכת)
   ├── פרופיל לקוח:  ניסוח פשוט, שאלות מותנות (״יש רכב?״ → תחבורה), טווחים, ״לא יודע/ת״
   └── פרופיל מאמנת: כל התשובות + שדות פנימיים + חישובים + פער מול התדפיסים + היסטוריית הגשות
```
דוגמה לשדה:
```js
{ id:'hou.rent', section:'housing', cat:'hou', item:'שכר דירה', type:'money',
  client:{ label:'כמה את/ה משלם/ת שכר דירה בחודש?', showIf:'housing.type=="rent"' },
  coach:{ compareTo:'report', flagIf:'value > income*0.4' } }
```
כך שינוי או הוספה של שאלה נעשים במקום אחד, ושני הטפסים נשארים מסונכרנים. כל הגשה נושאת `schemaVersion`, כדי שהגשות ישנות ימשיכו להיקלט נכון גם אחרי שהשאלון ישתנה.

## 5. תכנון האבטחה

### 5.1 הצפנה (ECIES על WebCrypto, בלי ספריות)
- **אצל המאמנת, פעם אחת:** המערכת יוצרת זוג מפתחות ECDH P-256. המפתח הפרטי נשמר ב־IndexedDB כ״לא ניתן לייצוא״. עותק גיבוי מוצפן בסיסמה (PBKDF2-SHA256, 600,000 סבבים, ו־AES-GCM) נשמר בשרת ומורד גם כקובץ שחזור.
- **אצל הלקוח, בכל הגשה:** הדפדפן יוצר מפתח חד־פעמי, גוזר ממנו מפתח הצפנה (ECDH ואז HKDF-SHA256) ומצפין ב־AES-256-GCM. לשרת נשלחת רק המעטפה:
  ```json
  { "v":1, "kid":"…", "epk":"…", "iv":"…", "ct":"…" }
  ```
- AES-GCM מזהה כל שינוי בטקסט המוצפן, ולכן אי אפשר לזייף או לשנות הגשה בלי שזה יתגלה.

### 5.2 הקישור
```
https://form.<domain>/#t=<טוקן 128 ביט>&k=<מפתח ציבורי, 87 תווים>
```
- הכול נמצא **אחרי `#`** (fragment). החלק הזה לא נשלח לשרת האירוח, לא נשמר בלוגים ולא עובר ב־Referrer.
- המפתח הציבורי נמצא בתוך הקישור עצמו. גם מי שמשתלט על האתר לא יכול להחליף אותו במפתח שלו בקישורים שכבר נשלחו.
- בשרת נשמר רק **SHA-256 של הטוקן**. דליפה של מסד הנתונים לא חושפת קישורים פעילים.
- לכל קישור יש תוקף (ברירת מחדל: 14 יום), אפשר לבטל אותו, ויש מגבלה של 5 הגשות.

### 5.3 הרשאות בשרת
| גורם | מה מותר לו |
|---|---|
| לקוח (anon) | **אין גישה לטבלאות בכלל.** רק שתי פונקציות: `form_open(token)` ו־`form_submit(token, envelope)`, עם בדיקת טוקן, תוקף, מגבלת גודל (2MB) ומגבלת הגשות |
| מאמנת | כניסה עם קוד במייל ו־**TOTP (אימות דו־שלבי)**. מדיניות RLS מחייבת `aal2` ובעלות על השורה |
| השרת עצמו | מחזיק רק טקסט מוצפן, את ה־hash של הטוקן ומזהה לקוח אטום (`client.id` אקראי, בלי שם) |

### 5.4 מחזור חיים של המידע
```
הוגש → נשמר מוצפן בשרת → נקלט אצל המאמנת → נמחק מהשרת אחרי 30 יום (משימה מתוזמנת)
```
המקום הקבוע של המידע נשאר המכשיר של המאמנת, בדיוק כמו היום.

### 5.5 הקשחה
- CSP קשיח: בטופס `default-src 'self'` ו־`connect-src` רק ל־Supabase. בטופס אין שום סקריפט צד שלישי, אין אנליטיקס ואין גופנים חיצוניים.
- כותרות HSTS, `X-Frame-Options: DENY` ו־`Referrer-Policy: no-referrer`. במערכת המאמנת: SRI לספריית xlsx.
- הטופס לא שואל לעולם על סיסמאות, קודים או מספרי כרטיס מלאים, ומציג הודעה על כך.
- טיוטה אצל הלקוח נשמרת בטלפון שלו, נמחקת אוטומטית אחרי ההגשה, ויש כפתור ״מחיקת הטיוטה מהמכשיר״.

### 5.6 רגולציה (ישראל)
המידע הוא מידע כלכלי אישי, ולכן חלים עליו חוק הגנת הפרטיות (כולל תיקון 13, בתוקף מאוגוסט 2025) ותקנות אבטחת מידע. התכנון עוזר לעמוד בדרישות: מזעור מידע, הצפנה, אימות דו־שלבי, אחסון באיחוד האירופי (יעד העברה מותר) ומחיקה אוטומטית. בנוסף נכין נוסח הסכמה ומדיניות פרטיות קצרה בטופס, ומסמך הגדרות מאגר. **מומלץ לעבור על הנוסחים עם עו״ד או יועץ פרטיות.** זה לא ייעוץ משפטי.

## 6. חוויית שימוש

### אצל המאמנת
1. בתיק הלקוח לוחצים **״שליחת שאלון ללקוח״**, ובוחרים סוג שאלון ותוקף.
2. מופיעים כפתורים: **וואטסאפ** (הודעה מוכנה עם הקישור), **מייל** ו**העתקה**.
3. בתיק רואים סטטוס חי: נשלח, נפתח, בתהליך, הוגש.
4. כשהגיע טופס: התראה במערכת (בזמן אמת) ובמייל (בלי פרטים אישיים, רק ״התקבל שאלון חדש״).
5. ב**תיבת השאלונים** רואים תצוגה מקדימה והבדלים מול מה שכבר יש בתיק, ואז לוחצים **״קליטה לתיק״**. התשובות נכנסות לתבנית הראשונית כעמודת **״מצב מוצהר״**, ליד ״מצב מצוי״ מהתדפיסים ו״תקציב״. **קליטה אף פעם לא דורסת תקציבים שכבר הזנת.** יש הגדרה לקליטה אוטומטית מלאה.

### אצל הלקוח
1. פותחים את הקישור מוואטסאפ. **בלי הרשמה ובלי סיסמה.**
2. מסך פתיחה עם הלוגו שלך, הסבר קצר, משך משוער ואייקון 🔒 ״המידע מוצפן ונגלה רק למאמנת״.
3. כ־6 שלבים עם סרגל התקדמות: פרטים כלליים, הכנסות, מגורים, הוצאות קבועות, משתנות, הלוואות ותשלומים, יעדים, ו(בשלב 2) העלאת תדפיסים.
4. מקלדת מספרים בטלפון, ״לא יודע/ת״, אפשר לצאת ולחזור והכול נשמר.
5. מסך סיכום, אישור הסכמה, הגשה ומסך תודה.

```
├── .github/workflows/ci.yml    ← בדיקות בכל push, ופינג שבועי ל־Supabase

```

## 11. מה נבנה בפועל (גרסה 2)

החלטות שהתקבלו: הלקוח ממלא רק את התבנית החודשית ולא מעלה תדפיסים. אין דומיין. ריפו ציבורי לדף GitHub Pages, וריפו פרטי למערכת המאמנת.

| רכיב | איפה | כתובת |
|---|---|---|
| טופס הלקוח | ריפו ציבורי `my-project` → GitHub Pages | `https://orelf001-tech.github.io/my-project/form/` |
| מערכת המאמנת | ריפו פרטי `cashflow-coach` → Netlify (מקור נפרד מהטופס) | `*.netlify.app` |
| תיבת הדואר המוצפנת | Supabase, אזור EU | — |
| קוד משותף (`shared/`) | ריפו ציבורי, ונמשך לפרטי כ־git submodule | — |

**למה שני מקורות (origins):** כל האתרים של משתמש ב־`github.io` חולקים מקור אחד, ולכן `localStorage` משותף. מערכת המאמנת, שמחזיקה את כל הלקוחות, יושבת ב־Netlify, כדי שדבר שקורה בטופס הציבורי לא יוכל להגיע אליה.

**שינויים מהתכנון:**
- **כניסת מאמנת:** סיסמה ואימות דו־שלבי (TOTP) במקום קוד במייל. כך אין תלות בהגדרות מייל, ויש חסימה מוחלטת: משתמש שאינו המאמנת מקבל ״אין הרשאה״ (`claim_coach`).
- **מילוי מראש:** הטופס מציג ללקוח את שמות הסעיפים מהתיק שלו. הרשימה מוצפנת במפתח שנמצא רק בקישור (`#p=`).
- **גיבוי מוצפן לענן:** כל הלקוחות נשמרים מוצפנים במפתח המאמנת, פעם ביום ואחרי כל קליטה (14 אחרונים). גיבוי כזה מאפשר לפתוח את המערכת במכשיר חדש.
- **קליטה:** לחודש חדש או לחודש קיים, לעמודת תקציב או שולם. אפשר להשאיר את הסכומים הקיימים או להחליף אותם. שורות לא נמחקות לעולם, וההוצאות השנתיות נקלטות כסכום חודשי (חלקי 12).
- **שמירת התשובות בתיק:** תשובות הלקוח נשמרות גם בתיק עצמו, כי העותק בשרת נמחק 30 יום אחרי הקליטה.

**בדיקות שעוברות:**
- בדיקות יחידה להצפנה, לתבנית ולקליטה (כולל ניסיונות זיוף של מעטפות).
- 11 בדיקות אבטחה למסד הנתונים מול Postgres אמיתי עם המיגרציה האמיתית.
- 8 בדיקות דפדפן מקצה לקצה: מאמנת ← קישור ← לקוח בטלפון ← קליטה ← מכשיר שני ← שחזור ← משתמש זר נחסם. בכולן אין שגיאות קונסול ואין הפרות CSP.
